# Preface

## What this book is

This book is for engineers who know how to use a mutex and want to know what is under it. You
learn concurrency by running it. Each chapter asks one question about threads, memory or the
processor and answers it in four steps:

1. **A tiny program.** A C function small enough to read in one glance, quoted from the
   repository that builds this book, never pasted.
2. **A run.** The same function, compiled to WebAssembly, on real threads in your browser: Web
   Workers sharing one memory. You set the workers and the iterations and read the result off
   the page.
3. **The instructions.** What the compiler emitted for that function on x86-64, AArch64, RISC-V
   and WebAssembly, generated by the build from the same source and labelled with the compiler
   and flags that produced them.
4. **One change.** The smallest edit that fixes the problem, run again; then, where it teaches
   something, one guarantee removed, to show why it was there.

The book's claim is that you should never have to believe the author when the computer can show
you. When a page says two threads lost increments, the count came from the threads. When it says
`x++` is three operations, the assembly is on the page.

## How a chapter works

Every chapter has the same sections, so you always know where you are:

1. **The question** it answers, and why the previous chapter left it open.
2. **The smallest program** that asks it.
3. **Run it**: the experiment, with the controls that matter to the concept, and what to try.
4. **What the source hides**: the operations one line became.
5. **At the machine**: the instructions for each target, generated and labelled.
6. **Fix one thing**: the smallest mechanism that addresses the problem.
7. **Break it again**: one guarantee removed, where removing it shows something.
8. **The mental model**: a compact statement later chapters reuse.
9. **What this cannot tell you**: the limits of the experiment, the fragments and the browser.
10. **Where to go next**: primary sources.

## Three ways to run an experiment

A concurrent program's result depends on the machine it runs on, so every experiment offers up to
three modes, and says which one you are looking at.

**Live.** The compiled kernel on real Web Workers. This needs shared memory, which a browser
grants only to a page served under two particular headers. The book arranges that for you, and
most browsers will run every experiment live. Where one will not, the page says so and offers
the other two modes; nothing in the book depends on a live run to be readable.

**Trace.** A deterministic model of the operations the program's threads perform, interleaved in
an order you choose or step through by hand. A lost update is forced on the page, step by step,
rather than left to luck. The trace is a model of the operations, not the compiled code, and
every trace says so.

**At a desk.** The commands that build the same kernel for pthreads and run it on your own
machine, where a measurement means more. [Appendix A](#reproducing-at-a-desk) has what you need.

## Two rules the book keeps

**No number is typed into the prose.** A count of lost updates, a time or a rate appears in an
experiment, computed as you watch, or in a trace, computed by the model. If the book says a run
on the author's machine lost half its increments, it is quoting the kind of thing you will see,
not a number you are asked to trust.

**No code is pasted into the prose.** Every C function is quoted from the repository by text
anchors, and every block of assembly was written by the build from that function, with the
compiler version and flags under it. Assembly that depends on a choice the book made (an
optimisation level, an architecture extension) says so where you read it.

## What the words mean

Four things that are often said in one breath are kept apart throughout:

- **The language's memory model**: what C promises a program that follows its rules, and what it
  refuses to promise one that does not.
- **The compiler**: what it did to your source on the way to instructions, and what it is
  allowed to do.
- **The instruction set**: what each instruction means on x86-64, AArch64, RISC-V and
  WebAssembly, and what each architecture may reorder.
- **The microarchitecture**: caches, store buffers and coherence, which the instruction set hides
  and the timings reveal.

When a result surprises, the chapter says which of the four is responsible.

## What you need

To read the book and run every experiment: a browser. To build the kernels at a desk: clang 18
with its WebAssembly linker, Python, Node, and a few minutes. [Appendix A](#reproducing-at-a-desk)
has the commands, and `make` in a fresh clone builds everything.

You should be comfortable reading C. The functions are deliberately plain, and every chapter says
what each quoted block does.

## Where this starts

[ch01](#what-x-plus-plus-does) takes one line, `counter++`, and shows the three operations it
became and the instructions four targets run for it. [ch02](#two-threads-one-variable) gives that
line to two threads and watches increments disappear.
